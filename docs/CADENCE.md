# Graphical evidence cadence (qa#17)

The scenario ladder is load-bearing only while its graphical evidence is
fresh. This document defines how often core lanes are refreshed, what
counts as stale, where staleness is reported, and how flaky lanes are
handled. Nothing here auto-executes graphical scenarios in hosted CI:
they need an approved KVM window (nested virtualization is not
available on the hosted runners), so the automated part is the
**staleness alarm**, not the execution.

## Refresh triggers

| Trigger | Obligation |
|---|---|
| New signed Preview ISO | Mandatory refresh of the core lanes (`install/*`, `smoke/*`, `session/*`, `controlcenter*`, `lock/*`, `recovery/*`) against the exact shipped artifact before the release is announced. |
| Weekly approved KVM window | Execute `keep` lanes whose evidence is stale (below), oldest first, on the base image pinned in `fixtures/`. Publishing the resulting bundles/sidecars updates the matrix. |
| Shell/Config/Greeter release without a new ISO | Refresh the lanes covering the changed surface; everything else ages normally. |

Manual executions through the install harness are recorded in
`docs/scenario-triage.yaml` rationales with the artifact SHA, exactly
like the install cells — they never appear as runner `PASS` in the
matrix until a tracked run bundle or sidecar exists.

## What counts as stale

A `keep` lane is stale when either holds:

1. Its latest tracked execution is older than **45 days** (machine
   alarm: `hornero-qa matrix --stale-days 45`), or it has never been
   executed.
2. It predates the newest change to the surface it covers (Shell,
   Config, Greeter, installer, hornero) — a human judgment recorded in
   the triage rationale at refresh time.

`fix` and `retire` lanes are excluded from the alarm: `fix` already
means known work, `retire` means gone.

## Where staleness is reported

- `docs/SCENARIO-MATRIX.md` (generated by `hornero-qa matrix`, checked
  in CI) is the ledger of record.
- `.github/workflows/evidence-staleness.yml` runs weekly (and on
  manual dispatch): it verifies the matrix is current and runs the
  staleness alarm, publishing the report in the job summary and
  failing the run while any core lane is stale. A red scheduled run
  is the alarm; fixing it means refreshing evidence, never editing
  the threshold to silence it.

## Flaky and quarantine policy

- **No silent retries.** A lane that fails intermittently is not
  re-run until it passes; the failure is the signal.
- A confirmed flaky lane gets a `fix` triage decision in
  `docs/scenario-triage.yaml` whose rationale links the tracking
  issue and the failure mode. That is the quarantine: explicit,
  dated, and owned — the lane leaves the staleness alarm while it is
  broken on purpose, and returns to `keep` only with a recorded
  passing execution.
- Retiring a lane (`retire`) requires the rationale to name what
  replaces its coverage.
